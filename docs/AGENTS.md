# PromoFM — Bug Diagnosis & Fix Protocol (Кодекс)

## Принципы

Этот кодекс — ЗАКОН. Нарушение ведёт к регрессиям, костылям и техдолгу.

### 1. Root Cause First

- **НЕ чини симптомы**, пока не найдена корневая причина.
- Баг в дочернем слое? Сначала проверь родительский/владеющий слой.
- Будь скептичен к фиксам в одном файле — обоснуй, почему другие слои не затронуты.

### 2. Fix at the Source of Truth

- Чини в слое-владельце (owner layer), а НЕ там, где симптом виден.
- Избегай компенсации в дочерних слоях (fallbacks, patches, дублирование логики, ветвление).

### 3. Ultra-Deep System Research

Перед любым фиксом — полное исследование end-to-end:

**Top-down:**
```
route → page → container → orchestration → state
```

**Bottom-up:**
```
function → hook → service → API → DB
```

### 4. Diagnose by Layers

Проверяй по слоям, в порядке приоритета:

1. **Data/Contracts** — типы, интерфейсы, API контракты
2. **Business Logic** — правила, валидация, трансформации
3. **Async/Timing** — race conditions, порядок операций, кэши
4. **UI State** — состояние компонентов, рендеринг, реактивность
5. **Integration** — связи между модулями, API вызовы
6. **Architecture** — структурные проблемы, паттерны

### 5. Aligned Layer Changes

При изменении механики — выровняй ВСЕ связанные слои:

- Контракты (типы, интерфейсы)
- Обработчики (handlers, controllers)
- Запросы (queries, mutations)
- Кэш (инвалидация)
- Сериализаторы (input/output)
- Состояния загрузки/ошибок (loading/error states)

### 6. Frontend Flow Inspection

Для фронтенд-багов — полная цепочка:

```
route → layout → page → hooks → API → backend
```

### 7. Proportional Fixes

- Предпочитай системные фиксы, но держи изменения пропорциональными.
- Если требуется ре-архитектура — определи scope, риски, совместимость, порядок деплоя.
- НЕ чини то, что не сломано. НЕ рефактори «заодно».

## Чеклист перед фиксом

- [ ] Корневая причина найдена и доказана
- [ ] Фикс в слое-владельце, а не в дочернем
- [ ] Все связанные слои проверены и выровнены
- [ ] Нет компенсирующей логики (fallbacks, patches)
- [ ] End-to-end flow проверен (top-down + bottom-up)
- [ ] Изменения пропорциональны проблеме

## Protected Assets

НЕ удалять, НЕ перезаписывать, НЕ модифицировать без явного запроса:

- `.env` файлы (секреты)
- `uploads/` директории (пользовательские данные)
- Миграции БД (только добавлять новые)
- SSL сертификаты и ключи
- systemd service файлы (без согласования)
- crontab записи (без согласования)
- Симлинки в `/var/www/` (ломаются при деплое!)
