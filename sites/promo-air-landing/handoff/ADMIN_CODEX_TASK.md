# Задача Codex: админка PROMO.AIR

Реализуй административную панель PROMO.AIR в действующем репозитории Promo.Music на основе dist/admin и приложенного макета. Прочитай AGENTS.md и ADMIN_SPEC.md. Сохрани существующие backend, auth, роли и billing. Начни с исследования кода, затем внедряй доступные компоненты и подключения, не ограничивайся общим планом.

Дизайн: лёгкая бело-голубая панель, постоянное левое меню, оранжевый active item, компактные данные, пространство между карточками. Структура: основная таблица слева, модерация и быстрые действия справа, журнал и помощь снизу. В левом меню именно «Финансы». Тариф остаётся полем заведения и действием назначения, не отдельным разделом. Design by Promo.Art.

В блоке «Полезные материалы» справа снизу использовать dist/assets/admin-dj.webp: герой с тёплой оранжево-коричневой кожей, чёрным худи, чёрными наушниками и коралловыми прямоугольными очками. Не подменять его красным/бирюзоволосым персонажем. Это локальная замена для админки, основной Нико в кабинете остаётся лысым в очках и наушниках. Слева в блоке помощи остаётся Мия.

Порядок:
1. Найди существующие admin route/guard, auth session, роли, сущности организаций/заведений/владельцев/устройств, endpoint модерации, тарифы, биллинг, поддержку и audit log. Запиши реальные точки подключения. Не придумывай URL API или соответствие demo-ID production-ID.
2. Перенеси dist/admin в компоненты принятого стека с текущим router и дизайн-токенами. Не заменяй production frontend статической папкой. Навигация, фильтры и dialogs из прототипа являются референсом поведения.
3. Подключи реальные серверные данные. Демо-числа, имена и финансы не переносить в рабочую БД. Нет интеграции: показать точное пустое/недоступное состояние, не симулировать успех.
4. Сервер проверяет права на каждую операцию. Администратор, модератор, финансовый сотрудник и поддержка имеют разные полномочия по существующей модели. Не давать административные права только на основании URL /admin/ или client-side role.
5. Одобрение/отклонение, блокировка/восстановление и назначение тарифа выполняются атомарно, с причиной, actor, временем, before/after и защитой от повторного решения. Смена статуса не должна автоматически стирать платёжные/правовые данные.
6. Раздел «Финансы»: реальные счета, платежи, возвраты, фильтры и сверка. Источник истинности billing/provider, суммы в minor units, отдельные финансовые права. В прототипе нет реальных списаний/возвратов, не добавлять их без существующего безопасного backend процесса.
7. «Написать владельцу» сейчас сохраняет локальный черновик. В production использовать существующую поддержку, явно различать draft/sent/delivery failed и проверять разрешения. Не отправлять сообщения при переносе или тестах.
8. Пройти проектные проверки, тесты ACL/модерации/финансов, browser QA desktop и mobile. Подготовить reviewable diff/PR и список подключённых систем/блокеров. Production rollout и миграции выполнять по принятому в проекте процессу и разрешению владельца.

Статический запуск из корня пакета: python3 -m http.server 8080 --directory dist, затем http://localhost:8080/admin/. Для полной интеграции см. ADMIN_SPEC.md. Тесты модели: node --test handoff/admin-model.test.cjs.
